\section{What is a distributed system?}

\begin{frameddefn}{Distributed system}
  A distributed system is a collection of autonomous processes $p_1, \ldots, p_n$, usually running on different machines, that cooperate to solve a common problem and that communicate \underline{only} by exchanging messages over a network.
\end{frameddefn}

The key word in the definition is \textit{only}: the processes don't share any memory and they don't share any clock. Everything a process knows about the others comes from the messages it has received, which may be arbitrarily old by the time they are read. Typical examples are replicated databases, cloud storage, blockchains, the DNS and large-scale web services.

Why do we build distributed systems in the first place? There are several reasons:
\begin{itemize}
  \item \textbf{Scalability}: a single machine has limited resources, while a distributed system can grow by adding machines.
  \item \textbf{Fault tolerance}: if data and computations are replicated on several machines, the system can keep working even when some of them fail.
  \item \textbf{Geographic distribution}: users and data are spread around the world, and serving them from nearby machines reduces latency.
  \item \textbf{Resource sharing}: different machines can share data, storage and computing power.
\end{itemize}

These advantages come at a price. Distributed systems are intrinsically hard because of three features that a single computer doesn't have:
\begin{enumerate}
  \item \textbf{Concurrency}: the processes run in parallel and interleave their actions in unpredictable ways.
  \item \textbf{No global clock}: each machine has its own clock and clocks are never perfectly synchronized, hence processes cannot agree on \textit{when} something happened.
  \item \textbf{Independent failures}: a machine or a link can fail while the rest of the system keeps working, and the other processes may not be able to tell a failed process from a slow one.
\end{enumerate}

A famous informal definition by Lamport captures the last point well: \emph{a distributed system is one in which a machine you have never heard of can crash and stop your own computer from working}.

\section{The system model}

To reason formally about algorithms we need a \textbf{model}, i.e. a precise list of assumptions on what processes and channels can and cannot do. The same problem can be easy in one model and impossible in another, so the model is always the first thing to check when reading a result.

\subsection{Processes}
The system is made of $n$ processes $\Pi = \{p_1, \ldots, p_n\}$. Each process executes a sequential program: it performs local computations, sends messages and receives messages, one step at a time.

  \caption{A process interacts with the upper layer (the application, which gives inputs and reads outputs) and with the link layer, through an InBuffer of received messages and an OutBuffer of messages to be sent. The state of a process is its internal memory together with the content of its InBuffer and OutBuffer.}
  \label{fig:process-model}
\end{figure}

\begin{frameddefn}{Process}
  A process $p_j$ is a (possibly infinite-state) input/output automaton made of:
  \begin{itemize}
    \item a set of \textit{internal states} $Q$, with a subset of \textit{initial states} $Q_{in} \subseteq Q$;
    \item the set $M$ of all possible \textit{messages}, each of the form $\abk{\text{sender}, \text{receiver}, \text{payload}}$;
    \item an \textit{input buffer} $\InBuf_j$, i.e. the multiset of messages received by $p_j$ and not yet processed;
    \item an \textit{output buffer} $\OutBuf_j$, i.e. the multiset of messages sent by $p_j$ that are still in flight (sent but not yet received);
    \item a \textit{transition function} $P_j$, which describes a single step of the process.
  \end{itemize}
\end{frameddefn}

The buffers are \textit{multisets} and not sets because the same message can be sent more than once, and they are not queues because, in general, the network doesn't preserve the order of messages.

In a single step, process $p_j$ reads its current state and all the messages in its input buffer, moves to a new state and produces a (possibly empty) set of messages to send. Formally, a step of $p_j$ is described as:
\begin{align*}
  P_j(q \in Q \cup Q_{in},\, \InBuf_j) &= (q' \in Q,\, \SendMsg \subseteq M) \\
  \OutBuf_j &\leftarrow \OutBuf_j \cup \SendMsg \\
  \InBuf_j &\leftarrow \varnothing
\end{align*}

In words: the transition function takes the current state $q$ and the received messages, and returns the next state $q'$ together with the set $\SendMsg$ of new messages. The new messages are added to the output buffer, while the input buffer is emptied, since all its messages have been consumed by the step.

\begin{framedobs}{}
  The process never moves messages from its output buffer to the input buffer of another process: this is done by the \textit{network}. Hence, an execution of the system alternates two kinds of steps:
  \begin{itemize}
    \item \textbf{computation steps}, in which a process $p_j$ applies $P_j$ as above;
    \item \textbf{delivery steps}, in which the network takes a message $m = \abk{p_i, p_j, \text{payload}}$ from $\OutBuf_i$ and puts it in $\InBuf_j$.
  \end{itemize}
  The assumptions on channels and timing that we discuss below are exactly assumptions on \textit{when} and \textit{in which order} delivery steps can happen.
\end{framedobs}

The \textbf{global state} (or \textit{configuration}) of the system is the collection of the states of all the processes together with the contents of all their buffers. We'll come back to global states later, where they will be central.

\subsection{Channels}
Unless stated otherwise, we assume that the network is \textit{fully connected} (every pair of processes can communicate directly) and that channels are \textbf{reliable}:
\begin{itemize}
  \item every message sent to a correct process is eventually received, i.e. it will be received after a finite (but unbounded) amount of time;
  \item every message is received at most once (no duplication);
  \item every received message was actually sent by someone (no creation).
\end{itemize}
Reliability says nothing about the order of delivery: messages can be delivered in a different order from the one in which they were sent. When we also require messages between the same pair of processes to be delivered in sending order, we speak of \textbf{FIFO channels}.

\subsection{Timing}

The process model tells us \textit{what} a process does in a step, but nothing about \textit{when} steps happen. Timing assumptions fill this gap: they describe how fast processes and the network are. There are three quantities involved:
\begin{itemize}
  \item \textbf{Process speed}: the time between two consecutive steps of the same process.
  \item \textbf{Message delay}: the time between the moment a message is put in the $\OutBuf$ of its sender and the moment it is delivered in the $\InBuf$ of its receiver.
  \item \textbf{Clock drift}: the rate at which the local clock of a process deviates from real time.
\end{itemize}

Depending on whether these quantities are bounded, and on whether the processes know the bounds, we obtain three timing models.

\begin{frameddefn}[label={def:timing-models}]{Timing models}
  A distributed system is:
  \begin{itemize}
    \item \textbf{synchronous} if there are \textit{known} upper bounds on process speed, on message delay and on clock drift;
    \item \textbf{asynchronous} if there are no bounds at all: steps and messages can take an arbitrary (but finite) amount of time;
    \item \textbf{eventually synchronous} (or \textit{partially synchronous}) if the bounds exist but are \textit{unknown} to the processes, or if they are known but hold only after some unknown point in time, called \textit{Global Stabilization Time} (GST).
  \end{itemize}
\end{frameddefn}

The synchronous model is the most convenient for the algorithm designer, since processes can reason about time, but it is also the least realistic. The asynchronous model is the opposite: it assumes nothing, so an algorithm that works in it works in any real network, but many problems become much harder (or even impossible) to solve. The eventually synchronous model is the compromise used by most practical systems.

\section{Executions}

The process model tells us what a single process does in a step. We now describe what a run of the \textit{whole} system looks like, and how the timing model constrains it.

\subsection{Configurations}

\begin{frameddefn}{Configuration}
  A configuration of the system is a vector containing the state of every process together with the content of all the buffers:
  \[C = \rbk{q_1, \ldots, q_n,\ \InBuf_1, \ldots, \InBuf_n,\ \OutBuf_1, \ldots, \OutBuf_n}\]
  A configuration is \textit{initial} if $q_j \in Q_{in}$ for every process $p_j$ and all the buffers are empty.
\end{frameddefn}

In other words, a configuration is a \curlyquotes{photograph} of the entire system at a given moment. The system moves from a configuration to the next one through a single \textbf{event} (or \textit{step}), which can be of two kinds:
\begin{itemize}
  \item a \textit{computation event} $\Exec(j)$, in which process $p_j$ applies its transition function $P_j$, empties $\InBuf_j$ and adds the new messages to $\OutBuf_j$;
  \item a \textit{delivery event} $\Del(i,j,m)$, in which the message $m$ sent by $p_i$ to $p_j$ is moved from $\OutBuf_i$ to $\InBuf_j$.
\end{itemize}

\begin{framedex}{The events of \Cref{fig:execution-steps}}
  In the computation event $\Exec(1)$, the transition function of $p_1$ is applied to its state and to the content of its input buffer:
  \begin{align*}
    P_1(q, \{m\}) &= (q', \{\abk{1,2,m'}\}) \\
    \OutBuf_1 &\leftarrow \OutBuf_1 \cup \{\abk{1,2,m'}\} \\
    \InBuf_1 &\leftarrow \varnothing
  \end{align*}
  In the delivery event $\Del(1,2,m')$ no process executes anything: the network moves the message from the output buffer of $p_1$ to the input buffer of $p_2$:
  \begin{align*}
    \OutBuf_1 &\leftarrow \OutBuf_1 \setminus \{\abk{1,2,m'}\} \\
    \InBuf_2 &\leftarrow \InBuf_2 \cup \{\abk{1,2,m'}\}
  \end{align*}
\end{framedex}

\begin{frameddefn}{Execution}
  An execution is an (infinite) alternating sequence of configurations and events
  \[\Exe = C_0,\ e_0,\ C_1,\ e_1,\ C_2,\ \ldots\]
  where $C_0$ is an initial configuration and each $C_{k+1}$ is the configuration obtained by applying the event $e_k$ to $C_k$.
\end{frameddefn}

We observe that events are \textit{atomic} and happen one at a time: even if in reality two processes act at the same instant, we can always describe the execution as an interleaving of their events, since a process cannot observe what another one is doing in the same instant. Not every sequence of events is acceptable, though: the timing model decides which executions are \textbf{admissible}. We now see the two extreme cases.

\subsection{Asynchronous executions}

In an asynchronous system there are no bounds on process speed and message delay. Hence, the order in which events happen is completely arbitrary. It's useful to think of it as chosen by a \textbf{scheduler} (or \textit{adversary}) that tries to make the algorithm fail: at every moment, it picks which process executes next and which message gets delivered. It can make a process very slow, deliver messages in any order and delay a message for as long as it wants. An algorithm is correct in the asynchronous model only if it is correct against \textit{every} possible scheduler.

\paragraph{Fairness.} There is only one thing that the scheduler can't do: postpone something forever.

\begin{frameddefn}{Fair execution}
  An execution $\Exe$ is fair if:
  \begin{enumerate}
    \item every process $p_i$ executes infinitely many local steps $\Exec(i)$;
    \item every message that is sent is eventually delivered by a $\Del(i,j,m)$ event.
  \end{enumerate}
\end{frameddefn}

Why do we need fairness? Without it the scheduler could prevent any progress, and no algorithm could ever achieve anything. For instance, the scheduler could:
\begin{itemize}
  \item never schedule $\Exec(j)$ for some process $p_j$, so that $p_j$ never does anything;
  \item keep a message $m$ in $\OutBuf_i$ forever, so that its receiver never learns about it.
\end{itemize}
Consider a process $p_1$ that sends a request to $p_2$ and waits for the answer. If the scheduler never delivers the request, or never lets $p_2$ execute, the answer never arrives and $p_1$ waits forever, even though no process has failed. No algorithm could guarantee that something good eventually happens, i.e. no algorithm could satisfy a liveness property. Fairness rules this out, but it doesn't say \textit{when} things happen: a message can still be delayed for an arbitrarily long (finite) time. In the following, the executions of an asynchronous system will always be assumed to be fair.

\paragraph{Local executions.} A single process doesn't see the whole execution: it only sees its own events and the messages delivered to it.

\begin{frameddefn}{Local execution}
  The local execution (or \textit{local view}) of process $p_j$ in an execution $\Exe$, denoted with $\Exe|p_j$, is the subsequence of the events of $\Exe$ that affect $p_j$, i.e. its computation events $\Exec(j)$ and the deliveries $\Del(i,j,m)$ of messages addressed to $p_j$, taken in their original order.
\end{frameddefn}

\begin{framedex}{}
  In the execution $\Exe$ of \Cref{fig:local-executions}, the local executions of $p_1$ and $p_2$ are:
  \[\Exe|p_1 = \rbk{\Del(0,1,m), \ldots} \qquad \Exe|p_2 = \rbk{\Del(3,2,m'), \ldots}\]
  Process $p_1$ only sees that $m$ has arrived: it doesn't see $e_2$ and $e_3$, and it doesn't know whether they happened before or after $e_1$.
\end{framedex}

The execution $\Exe'$ in \Cref{fig:local-executions} is different from $\Exe$: the events of $p_3$ and $p_2$ happen \textit{before} the ones of $p_0$ and $p_1$, so the two executions go through different configurations. However, every process sees exactly the same thing in both executions:
\[\Exe|p_j = \Exe'|p_j \quad \text{for every } j \in \{0,1,2,3\}\]
Hence, different executions can give the same local executions. When this happens for a process $p_j$, we say that $p_j$ \textbf{cannot distinguish} $\Exe$ from $\Exe'$: no matter what algorithm it runs, its states and its messages are exactly the same in the two executions, since they only depend on its local execution.

\begin{frameddefn}{Indistinguishability}
  Two executions $\Exe$ and $\Exe'$ are indistinguishable for process $p_j$ if $\Exe|p_j = \Exe'|p_j$. They are indistinguishable if they are indistinguishable for every process, i.e. if $\Exe|p_j = \Exe'|p_j$ for all $j$.
\end{frameddefn}

The example generalizes. Consider two consecutive events of an execution that affect different processes and such that the second one is not the delivery of a message produced by the first one. Swapping them doesn't change any local execution, and the resulting execution is still fair. Repeating such swaps, we can build many executions which are all indistinguishable from the original one, even though they go through different configurations. This leads to a fundamental result.

\begin{framedthm}{}
  In an asynchronous system it is impossible to reconstruct the exact execution.
\end{framedthm}

\begin{proof}[Proof idea]
  Everything a process knows comes from its local execution, and every piece of information it can share with the others is a message produced by its transition function, which again only depends on its local execution. By the above argument, for most executions $\Exe$ there is a different execution $\Exe'$ such that $\Exe|p_j = \Exe'|p_j$ for every $j$. In $\Exe$ and $\Exe'$ every process goes through the same states and sends the same messages, hence no process, and no observer that only receives information from the processes, can tell whether the real execution was $\Exe$ or $\Exe'$.
\end{proof}

\begin{framedobs}{}
  This is why, in an asynchronous system, we can't rely on the real order of events. What processes \textit{can} know is the order imposed by their local executions and by messages: in \Cref{fig:local-executions}, $e_0$ must come before $e_1$ in every execution, since $m$ can't be delivered before being sent, while the relative order of $e_0$ and $e_2$ can't be determined. This is exactly the idea behind the happened-before relation, which we'll define later in the course.
\end{framedobs}

\subsection{Synchronous executions}

In this course we will see three definitions of synchrony:
\begin{itemize}
  \item \textbf{asynchronous systems}, discussed above;
  \item \textbf{eventually-synchronous systems}, which behave asynchronously for an unknown (but finite) amount of time and then become synchronous (module M2);
  \item \textbf{synchronous systems}.
\end{itemize}

\begin{frameddefn}{Synchronous system}
  A system is synchronous if there is:
  \begin{itemize}
    \item a fixed bound on the delay of messages;
    \item a fixed bound on the execution time of the actions executed by processes;
    \item a fixed bound on the time between the execution of two actions.
  \end{itemize}
\end{frameddefn}

With these bounds, the processes can organize the computation in \textbf{rounds}: each round lasts a fixed amount of time, long enough for every process to execute a step and for every message to arrive, and a process simply waits for the end of the round before reading its input buffer. This gives the following execution model.

\begin{frameddefn}{Synchronous execution}
  An execution is a synchronous execution if it is divided into rounds $1, 2, 3, \ldots$ such that, in each round:
  \begin{enumerate}
    \item every process executes exactly one computation event $\Exec(j)$;
    \item every message sent during the round is delivered before the next round starts.
  \end{enumerate}
\end{frameddefn}

In other words, in each round every process reads all the messages sent to it in the previous round, updates its state and sends its new messages, which will be read in the next round. All the processes move in \textit{lockstep}, like musicians following the same metronome.

\begin{framedobs}{}
  If the processes don't fail and the algorithm is deterministic, a synchronous execution is completely determined by the initial configuration: the order of the events inside a round doesn't matter, since every message is read only in the next round. In the asynchronous model, instead, the same initial configuration gives rise to infinitely many different executions, one for each choice of the scheduler. This is why proving correctness is so much harder in the asynchronous model.
\end{framedobs}

\begin{framedobs}{}
  Every synchronous execution is also a fair asynchronous execution: in each round every process takes a step and every message is delivered, so both fairness conditions hold. Hence, an algorithm that is correct for every asynchronous execution is also correct for every synchronous one.
\end{framedobs}

The rounds also give a natural way to measure time:
\begin{itemize}
  \item in the synchronous model, the \textbf{time complexity} of an algorithm is the number of rounds it needs;
  \item in the asynchronous model, we normalize the maximum message delay of the execution to $1$ time unit and measure time in these units.
\end{itemize}

\section{Models for process failures}

So far we have assumed that every process always follows its automaton. In a real system, however, machines crash, software has bugs and some nodes may even be controlled by an attacker. A \textbf{failure model} describes \textit{how} a process can deviate from its expected behaviour. There are two main models:
\begin{itemize}
  \item \textbf{crash-stop failures}, in which a process simply stops;
  \item \textbf{Byzantine failures}, in which a process can behave in an arbitrary way.
\end{itemize}

We observe that failure models are \textit{independent} from timing models: we can consider crash failures in a synchronous system, Byzantine failures in an asynchronous one, and so on. To describe failures inside an execution, we add a new kind of event for each model.

\subsection{Crash-stop failures}

\begin{frameddefn}{Crash-stop failure}
  The event $\Crash(j)$ represents the crash of process $p_j$. After this event, $p_j$ does nothing: every following $\Exec(j)$ leaves its state unchanged and sends no messages. A process that crashes never recovers.
\end{frameddefn}

The crash only affects the process, not the network. Hence, the messages that $p_j$ had already put in $\OutBuf_j$ before crashing can still be delivered, and the messages addressed to $p_j$ can still be delivered into $\InBuf_j$, but $p_j$ will never read them.

\subsection{Byzantine failures}

\begin{frameddefn}{Byzantine failure}
  The event $\Byz(j)$ represents a Byzantine failure of process $p_j$. After this event, $p_j$ behaves in an arbitrary way: when we have $\Exec(j)$, we no longer follow the automaton of $p_j$, so its state can change arbitrarily and it can send any message to any process.
\end{frameddefn}

A Byzantine process can do anything: send wrong values, send \textit{different} values to different processes, pretend to have received messages it never got, stay silent for a while and then come back, or coordinate with other Byzantine processes. Byzantine failures model both arbitrary software and hardware faults and \textbf{malicious} behaviour, e.g.\ a node controlled by an attacker. This is why they are central in security-related systems such as blockchains.

\subsection{Comparing the two models}

A Byzantine process can behave in \textit{any} way, and in particular it can decide to stop doing anything forever. Hence, every behaviour of a crashed process is also a possible behaviour of a Byzantine process: crash-stop failures are a special case of Byzantine failures.

\begin{framedobs}{}
  An algorithm that tolerates $f$ Byzantine processes also tolerates $f$ crashed processes, but not vice versa. Tolerating Byzantine failures is much more expensive: typically, it requires more processes, more messages and more rounds. For example, many problems that can be solved with $n > 2f$ processes under crash failures need $n > 3f$ processes under Byzantine failures.
\end{framedobs}

\subsection{Correct processes and the bound on failures}

\begin{frameddefn}{Correct and faulty processes}
  A process is \textbf{correct} in an execution if it never experiences a failure event, i.e. neither $\Crash(j)$ nor $\Byz(j)$ appears in the execution. Otherwise, it is \textbf{faulty}.
\end{frameddefn}

We stress that being correct is a property of the \textit{whole} execution, and that the processes don't know who is correct. In an asynchronous system this is unavoidable: a crashed process and a very slow one produce the same local executions at every other process, so they are indistinguishable. At any moment, a process that has been silent for a long time may have crashed or may be about to send its next message.

\begin{frameddefn}{Failure bound}
  We denote with $f$ the maximum number of processes that can experience a failure event in an execution.
\end{frameddefn}

Usually we bound $f$, since without any bound no algorithm can guarantee anything. A natural bound is $f \leq n-1$, meaning that at least one process is correct. Many algorithms require stronger bounds, such as $f < n/2$ (a majority of correct processes) or $f < n/3$, and the bound on $f$ will be one of the first things to check for every algorithm we'll see.

Finally, we \textbf{never} make assumptions on \textit{when} a failure event happens. A failure can occur at any point of the execution: at the very beginning, in the middle of a protocol or right before the last step. As for the order of events, it's useful to think that the scheduler also chooses \textit{which} processes fail (at most $f$ of them) and \textit{when}, and it will choose the worst possible moment for the algorithm.

\begin{framedobs}{}
  With failures, the fairness conditions of an asynchronous execution only apply to correct processes: a crashed process stops executing local steps, and there is no guarantee on the messages it would have sent after crashing.
\end{framedobs}

\section{Distributed abstractions}

\subsection{The road to build a distributed abstraction}\label{sec:road}

Now that we have a precise model of processes, executions and failures, we can describe the general method that we'll follow for every problem in this course. Building a distributed abstraction always goes through four steps:
\begin{enumerate}
  \item \textbf{Define a system model}: which timing model (synchronous, asynchronous, \ldots), which failure model (crash-stop, Byzantine) and how many failures $f$ we tolerate.
  \item \textbf{Formalize the problem with an abstraction}: design an abstract formal object that captures the problem that we want to solve, and specify \textit{unambiguously} the properties that it must satisfy.
  \item \textbf{Implement the abstraction} with a distributed protocol, i.e. an automaton for each process.
  \item \textbf{Prove that the protocol implements the abstraction}, i.e. that every execution of the protocol in the chosen system model satisfies all the properties of the abstraction.
\end{enumerate}

The second step is the most delicate one. An abstraction is described only by its \textit{interface} (the events through which it interacts with the outside world) and by its \textit{properties}, without saying anything about how it is implemented. This allows us to use an abstraction as a black box to build more complex ones: once we have proved that a protocol implements it, we can forget about the protocol and only use the properties.

\paragraph{Interface of an abstraction.} Each abstraction is a module that lives inside every process and communicates with the layers above and below it through events, as in \Cref{fig:process-model}:
\begin{itemize}
  \item \textbf{requests} are events that the upper layer (the application, or another abstraction) sends \textit{to} the module, asking it to do something;
  \item \textbf{indications} are events that the module sends \textit{to} the upper layer, notifying it that something has happened.
\end{itemize}
We write events as $\abk{\textit{Name} \mid \textit{parameters}}$.

\subsection{Abstracting a real communication link}

As a first example, we apply the method to the most basic component of a distributed system: the communication link between two processes. Real networks are not reliable: packets get lost because of congestion or corrupted bits, they may be retransmitted and duplicated by lower layers, but at least they are not invented by the network. Informally, we have:

\begin{framedobs}{Informal description}
  We have a link that loses messages with a certain probability $pr$, the channel can duplicate a message a finite number of times, and it does not create messages from thin air.
\end{framedobs}

This description is intuitive but not precise enough to prove anything. In particular, the probability $pr$ is annoying: we would like to reason about executions without computing probabilities. The idea is to capture only its \textit{consequence}: if a message is sent over and over again, sooner or later one of the copies gets through. Indeed, if each copy is lost independently with probability $pr < 1$, the probability that the first $k$ copies are all lost is $pr^k$, which goes to $0$ as $k \to \infty$.

\paragraph{Interface.} A link exposes two events:
\begin{itemize}
  \item \textbf{Request} $\abk{\textit{Send} \mid q, m}$: send a message $m$ to process $q$;
  \item \textbf{Indication} $\abk{\textit{Deliver} \mid p, m}$: deliver a message $m$ sent by process $p$.
\end{itemize}

\paragraph{Properties.} The informal description is turned into three properties.

\begin{frameddefn}[label={def:fair-lossy}]{Fair-lossy link}
  A fair-lossy link satisfies the following properties:
  \begin{itemize}[leftmargin=3.4em]
    \item[\textbf{FL1}] \textbf{(Fair-loss)} If a correct process $p$ sends $m$ infinitely often to a correct process $q$, then $q$ delivers $m$ an infinite number of times.
    \item[\textbf{FL2}] \textbf{(Finite duplication)} If a correct process $p$ sends $m$ a finite number of times to $q$, then $q$ cannot deliver $m$ an infinite number of times.
    \item[\textbf{FL3}] \textbf{(No creation)} If some process $q$ delivers a message $m$ with sender $p$, then $m$ was sent by $p$ to $q$.
  \end{itemize}
\end{frameddefn}

Each property corresponds to a piece of the informal description:
\begin{itemize}
  \item FL1 captures \curlyquotes{loses messages with a certain probability}: the link can lose any single message, but it can't lose \textit{all} the copies of a message that is sent infinitely many times. We observe that both processes must be correct: if $q$ crashes, it obviously can't deliver anything.
  \item FL2 captures \curlyquotes{can duplicate a message a finite number of times}: duplicates are allowed, but only finitely many for each send.
  \item FL3 captures \curlyquotes{does not create messages from thin air}: every delivered message was really sent, and by the process that appears as its sender.
\end{itemize}

\subsection{Safety and liveness properties}

When we specify an abstraction, its properties are usually of two very different kinds, and specifications typically combine both of them.

\begin{frameddefn}[label={def:safety}]{Safety property}
  A safety property is a property that, if violated at some time $t$, can never be satisfied after $t$. Formally, if a safety property is violated in an execution $\Exe$, then there is a finite prefix $\Exe'$ of $\Exe$ such that \textit{any} extension of $\Exe'$ also violates the property.
\end{frameddefn}

Informally, a safety property states that \textbf{something bad cannot happen}. If the bad thing happens, we can point to the exact moment in which it happened, and nothing that happens later can repair it.

\begin{frameddefn}[label={def:liveness}]{Liveness property}
  A liveness property is a property that cannot be violated in a finite execution. Formally, for any finite execution $\Exe$ that does not satisfy a liveness property, there is an extension of $\Exe$ that satisfies it.
\end{frameddefn}

Informally, a liveness property states that \textbf{something good will eventually happen}. At any finite moment the good thing may not have happened yet, but there is always hope that it will happen later.

\paragraph{Classifying the properties of a fair-lossy link.} Let's apply the definitions to the three properties of \Cref{def:fair-lossy}.

\begin{framedprob}{}
  Among FL1, FL2 and FL3 there is at least one safety property. Which one?
\end{framedprob}

\textit{Solution:} FL3 (no creation) is a safety property. Suppose that in an execution $\Exe = (e_1, e_2, e_3, e_4, e_5, \ldots)$ the event $e_4$ is the delivery to $q$ of a message $m$ that was never sent by anyone. Then FL3 is violated already in the finite prefix $\Exe' = (e_1, e_2, e_3, e_4)$, and it stays violated in every extension of $\Exe'$: no future event can \curlyquotes{un-deliver} $m$.

\begin{framedprob}{}
  Among FL1, FL2 and FL3 there is at least one liveness property. Which one?
\end{framedprob}

\textit{Solution:} FL1 (fair-loss) is a liveness property. If $p$ has sent a message $m$ and $q$ has not delivered it at time $t$, there is always hope that it will be delivered at time $t + \Delta$. Formally, take any finite execution, e.g. $\Exe = (e_1, e_2, e_3, e_4, e_5)$: we can always extend it by letting $p$ send $m$ again and again and adding infinitely many deliveries, e.g. starting with $\Exe' = (e_1, e_2, e_3, e_4, e_5, \Del(p,q,m), \ldots)$, so that FL1 is satisfied.

\begin{framedprob}{}
  Is FL2 (finite duplication) a safety or a liveness property?
\end{framedprob}

\textit{Solution:} FL2 is a liveness property, even though it sounds like \curlyquotes{something bad cannot happen}. The bad thing here is an \textit{infinite} number of deliveries, which can never be observed in a finite execution. Take any finite execution in which $q$ has delivered $m$ many times:
\[\Exe = (\Del(p,q,m), \Del(p,q,m), \ldots, \Del(p,q,m))\]
We can always extend it as
\[\Exe' = (\Del(p,q,m), \ldots, \Del(p,q,m), e_1, e_2, e_3, \ldots)\]
where no $e_j$ is $\Del(p,q,m)$. In $\Exe'$ the message $m$ is delivered only finitely many times, so FL2 is satisfied. Hence, no finite execution violates FL2, which is exactly the definition of liveness.

\begin{framedprob}{}
  Consider the following variant of FL2:
  \begin{itemize}
    \item[] \textbf{(At-most-7 duplication)} For each message identifier $m$, process $q$ delivers $m$ at most seven times.
  \end{itemize}
  Is it a liveness property?
\end{framedprob}

\textit{Solution:} No, it is a safety property. Consider the finite execution
\[\Exe = (\underbrace{\Del(p,q,m), \ldots, \Del(p,q,m)}_{8 \text{ times}})\]
After the eighth delivery of $m$ the property is violated, and every extension of $\Exe$ still violates it, since the eight deliveries can't be undone.

\begin{framedobs}{}
  The two duplication properties look almost identical, but they are of different kinds. The difference is \textit{when} the bad thing becomes visible: \curlyquotes{more than 7 deliveries} is detected after a finite number of events, while \curlyquotes{infinitely many deliveries} is never detected in finite time. A bound that is fixed in advance gives a safety property, \curlyquotes{finitely many} gives a liveness property.
\end{framedobs}

\paragraph{Other properties.} The same classification applies to any abstraction. For instance, consider a resource $r$ (e.g.\ a file or a printer) that processes want to use exclusively:
\begin{itemize}
  \item \textbf{Mutual exclusion}: if a process $p$ is granted a resource $r$ at time $t$, then no other process $q$ is granted $r$ at $t$.
  \item \textbf{No-deadlock}: if $r$ is not already granted, eventually someone gets a grant on resource $r$.
  \item \textbf{No-starvation}: if a process $p$ requests a grant on resource $r$, it will eventually get it.
\end{itemize}

\begin{framedprob}{}
  Classify mutual exclusion, no-deadlock and no-starvation as safety or liveness properties.
\end{framedprob}

\textit{Solution:} Mutual exclusion is a safety property: if at some time $t$ two processes hold $r$, the violation is visible in the finite prefix that ends at $t$, and it can't be repaired. No-deadlock and no-starvation are liveness properties: they both contain \curlyquotes{eventually}, and at any finite time the grant may still arrive later. We also observe that no-starvation is stronger than no-deadlock: no-deadlock only requires that \textit{someone} gets the resource, while no-starvation requires that \textit{every} process that asks for it gets it.

\paragraph{Badly written properties.} A good specification keeps safety and liveness separate, since they are proved with different techniques: safety is usually proved with an invariant (\curlyquotes{in every reachable configuration, nothing bad has happened}), while liveness requires showing that progress is eventually made.

\begin{framedprob}{}
  What is wrong with the following property?
  \begin{itemize}
    \item[] If process $p$ sends a message $m$ to $q$, then $q$ will eventually deliver it and this delivery is unique.
  \end{itemize}
\end{framedprob}

\textit{Solution:} The property mixes two different aspects:
\begin{itemize}
  \item a liveness aspect: $q$ will eventually deliver $m$;
  \item a safety aspect: the delivery is unique.
\end{itemize}
It should be decomposed into two properties:
\begin{enumerate}
  \item If $p$ sends a message $m$ to $q$, then $q$ eventually delivers it. \hfill (liveness)
  \item If $p$ sends a message $m$ to $q$, then $m$ is delivered at most once. \hfill (safety)
\end{enumerate}

\begin{framedobs}{}
  This is not a coincidence: it can be proved (Alpern and Schneider, 1985) that \textit{every} property of executions can be written as the conjunction of a safety property and a liveness property. Hence, the decomposition we did above can always be done.
\end{framedobs}

\subsection{Stubborn links}

The first problem of a fair-lossy link is that a single send may never be delivered: to exploit FL1, the sender has to send the message infinitely often. A stubborn link hides this retransmission from the upper layer.

\begin{frameddefn}{Stubborn link}
  A stubborn link exposes the request $\abk{\textit{sl}, \textit{Send} \mid q, m}$ and the indication $\abk{\textit{sl}, \textit{Deliver} \mid p, m}$, and satisfies:
  \begin{itemize}[leftmargin=3.4em]
    \item[\textbf{SL1}] \textbf{(Stubborn delivery)} If a correct process $p$ sends $m$ \underline{once} to a correct process $q$, then $q$ delivers $m$ an infinite number of times.
    \item[\textbf{SL2}] \textbf{(No creation)} If some process $q$ delivers a message $m$ with sender $p$, then $m$ was sent by $p$ to $q$.
  \end{itemize}
\end{frameddefn}

The implementation is straightforward: the sender keeps every message it has sent and retransmits all of them periodically, forever.

\begin{framedalgo}[label={alg:retransmit}, unbreakable]{Retransmit Forever (stubborn link at process $p$)}
  \textbf{Implements:} stubborn link, instance \textit{sl}. \quad \textbf{Uses:} fair-lossy link, instance \textit{fll}.
  \begin{algorithmic}[1]
    \Upon{$\abk{\textit{sl}, \textit{Init}}$}
      \State $\textit{sent} \gets \varnothing$
      \State $\textit{starttimer}(\Delta)$
    \EndUpon
    \Upon{$\abk{\textit{Timeout}}$}
      \ForAll{$(q, m) \in \textit{sent}$}
        \State \Trigger $\abk{\textit{fll}, \textit{Send} \mid q, m}$
      \EndFor
      \State $\textit{starttimer}(\Delta)$
    \EndUpon
    \Upon{$\abk{\textit{sl}, \textit{Send} \mid q, m}$}
      \State \Trigger $\abk{\textit{fll}, \textit{Send} \mid q, m}$
      \State $\textit{sent} \gets \textit{sent} \cup \{(q, m)\}$
    \EndUpon
    \Upon{$\abk{\textit{fll}, \textit{Deliver} \mid p', m}$}
      \State \Trigger $\abk{\textit{sl}, \textit{Deliver} \mid p', m}$
    \EndUpon
  \end{algorithmic}
\end{framedalgo}

\begin{proof}[Correctness]
  \textit{SL1}: if the correct process $p$ sends $m$ to $q$, then $(q,m)$ is added to \textit{sent} and never removed. Since $p$ is correct, its timer expires infinitely many times, so $p$ sends $m$ to $q$ over \textit{fll} infinitely often. By FL1, $q$ \textit{fll}-delivers $m$ infinitely many times, and every \textit{fll}-delivery triggers an \textit{sl}-delivery. \textit{SL2}: every \textit{sl}-delivery comes from an \textit{fll}-delivery, so it follows directly from FL3.
\end{proof}

\begin{framedobs}{}
  The timer is only used to space out retransmissions: the algorithm doesn't need any assumption on timing, so it works in an asynchronous system. Of course it is very inefficient, since messages are retransmitted forever. In practice, the receiver sends acknowledgements and the sender stops retransmitting acknowledged messages.
\end{framedobs}

\subsection{Perfect point-to-point links}

A stubborn link delivers every message infinitely many times, which is not what an application wants. The perfect link removes the duplicates.

\begin{frameddefn}[label={def:perfect-link}]{Perfect point-to-point link}
  A perfect point-to-point link exposes the request $\abk{\textit{pl}, \textit{Send} \mid q, m}$ and the indication $\abk{\textit{pl}, \textit{Deliver} \mid p, m}$, and satisfies:
  \begin{itemize}[leftmargin=3.4em]
    \item[\textbf{PL1}] \textbf{(Reliable delivery)} If a correct process $p$ sends $m$ to a correct process $q$, then $q$ eventually delivers $m$.
    \item[\textbf{PL2}] \textbf{(No duplication)} A message is delivered at most once.
    \item[\textbf{PL3}] \textbf{(No creation)} If some process $q$ delivers a message $m$ with sender $p$, then $m$ was sent by $p$ to $q$.
  \end{itemize}
\end{frameddefn}

\begin{framedalgo}[label={alg:eliminate-duplicates}, unbreakable]{Eliminate Duplicates (perfect link at process $p$)}
  \textbf{Implements:} perfect point-to-point link, instance \textit{pl}. \quad \textbf{Uses:} stubborn link, instance \textit{sl}.
  \begin{algorithmic}[1]
    \Upon{$\abk{\textit{pl}, \textit{Init}}$}
      \State $\textit{delivered} \gets \varnothing$
    \EndUpon
    \Upon{$\abk{\textit{pl}, \textit{Send} \mid q, m}$}
      \State \Trigger $\abk{\textit{sl}, \textit{Send} \mid q, m}$
    \EndUpon
    \Upon{$\abk{\textit{sl}, \textit{Deliver} \mid p', m}$}
      \If{$m \notin \textit{delivered}$}
        \State $\textit{delivered} \gets \textit{delivered} \cup \{m\}$
        \State \Trigger $\abk{\textit{pl}, \textit{Deliver} \mid p', m}$
      \EndIf
    \EndUpon
  \end{algorithmic}
\end{framedalgo}

\begin{proof}[Correctness]
  \textit{PL1}: by SL1, $q$ \textit{sl}-delivers $m$ infinitely many times, and the first time $m \notin \textit{delivered}$, so $q$ \textit{pl}-delivers it. \textit{PL2}: after the first \textit{pl}-delivery, $m \in \textit{delivered}$ forever, so every later copy is discarded. \textit{PL3}: every \textit{pl}-delivery comes from an \textit{sl}-delivery, so it follows from SL2.
\end{proof}

\begin{framedobs}{}
  The algorithm identifies a message by its \textit{content}: two messages are the same if and only if they are equal. This is fine only if every message sent is unique, e.g.\ because it contains a unique identifier. If the application sends the same content twice, the second message is discarded as a duplicate of the first. The next exercise shows why this matters.
\end{framedobs}

\subsection{Exercise: the counting server}

\begin{framedprob}[label={prob:counting-server}]{}
  You built a \textbf{counting server} that communicates with you using our perfect point-to-point link algorithm over a stubborn link. The server stores a variable $v$ (initially equal to $0$) and it exposes three operations:
  \begin{itemize}
    \item $\texttt{INC}$: increases the value of $v$ by $1$;
    \item $\texttt{DEC}$: decreases the value of $v$ by $1$;
    \item $\texttt{GET}$: invokes $\abk{\textit{pl}, \textit{Send} \mid \textit{client}, v}$, where \textit{client} is your name as a process.
  \end{itemize}
  The server executes an operation when it delivers the corresponding message: for example, the increase happens when the server sees the event $\abk{\textit{pl}, \textit{Deliver} \mid \textit{client}, \texttt{INC}}$.

  You act as a client and you invoke exactly three operations, in the following order:
  \[\abk{\textit{pl}, \textit{Send} \mid \textit{server}, \texttt{INC}},\quad \abk{\textit{pl}, \textit{Send} \mid \textit{server}, \texttt{INC}},\quad \abk{\textit{pl}, \textit{Send} \mid \textit{server}, \texttt{GET}}\]
  You are really puzzled when, after a while, you see $\abk{\textit{pl}, \textit{Deliver} \mid \textit{server}, 1}$ on your client. Startled, you ask again $\abk{\textit{pl}, \textit{Send} \mid \textit{server}, \texttt{GET}}$. Unfortunately, you are still waiting for an answer.

  What is happening? Is there any way to fix it? There are two possible explanations: try to find both. \textit{Hint: one of them comes from the question \curlyquotes{how long will you wait for an answer?}}
\end{framedprob}

\textit{Solution:} We expected $v = 2$, but we got $1$.

\paragraph{Explanation 1: messages out of order.} A perfect link guarantees that every message is delivered exactly once, but it says \underline{nothing} about the order of delivery. Hence, the server may deliver the first $\texttt{INC}$, then the $\texttt{GET}$, and only then the second $\texttt{INC}$: when it answers the $\texttt{GET}$, the value is $v = 1$.

This also explains why we are still waiting for the second answer: the system is asynchronous, so there is no bound on message delays and the answer to the second $\texttt{GET}$ may simply still be in transit. We can't wait for a fixed amount of time and conclude that it got lost: we just have to keep waiting.

\paragraph{Explanation 2: duplicates.} Even if the messages are delivered in order, the scenario happens if we use the Eliminate Duplicates algorithm (\Cref{alg:eliminate-duplicates}). The server receives the first $\texttt{INC}$ and adds it to \textit{delivered}. When the second $\texttt{INC}$ arrives, it has exactly the same content, so the server thinks it is a duplicate and discards it: $v$ stays equal to $1$, and the $\texttt{GET}$ correctly returns $1$. For the same reason, our second $\texttt{GET}$ is identical to the first one, so it is discarded too, and we will wait forever.

\paragraph{How to fix it.} Both problems are solved by attaching a \textbf{sequence number} to every message:
\begin{itemize}
  \item the sequence number makes every message unique, so two $\texttt{INC}$ with the same content are no longer considered duplicates (explanation 2);
  \item the receiver can use the sequence numbers to deliver the messages in the order in which they were sent (explanation 1).
\end{itemize}
The second point is exactly what a FIFO link does.

\subsection{FIFO perfect links}

\begin{frameddefn}{FIFO perfect link}
  Each link instance connects a fixed pair of processes $p$ and $q$. A FIFO perfect link satisfies PL1 (reliable delivery), PL2 (no duplication) and PL3 (no creation) of a perfect link, and moreover:
  \begin{itemize}[leftmargin=3.4em]
    \item[\textbf{FIFO}] \textbf{(FIFO delivery)} If some process delivers $m$ before $m'$, where $m$ and $m'$ were sent by the same process $p$, then $p$ sent $m$ before $m'$.
  \end{itemize}
\end{frameddefn}

\begin{framedobs}{}
  The FIFO property only concerns messages sent by the \textit{same} process to the same receiver: messages coming from different senders can still be delivered in any order. On the slides, the third property is called FL3: it is the same no-creation property of the other links, here called PL3.
\end{framedobs}

The implementation adds a sequence number to every message, separately for each destination, and the receiver delivers the messages of each sender following the sequence numbers.

\begin{framedalgo}[label={alg:fifo}, unbreakable]{FIFO perfect links at process $p_i$}
  \textbf{Implements:} FIFO perfect point-to-point links, instance \textit{fpl}. \quad \textbf{Uses:} perfect point-to-point links, instance \textit{pl}.
  \begin{algorithmic}[1]
    \Upon{$\abk{\textit{fpl}, \textit{Init}}$}
      \State $\textit{pending} \gets \varnothing$
      \ForAll{$q \in \Pi$}
        \State $\textit{seq}[q] \gets 0$ \Comment{last sequence number sent to $q$}
        \State $\textit{next}[q] \gets 1$ \Comment{next sequence number expected from $q$}
      \EndFor
    \EndUpon
    \Upon{$\abk{\textit{fpl}, \textit{Send} \mid q, m}$}
      \State $\textit{seq}[q] \gets \textit{seq}[q] + 1$
      \State \Trigger $\abk{\textit{pl}, \textit{Send} \mid q, [\textit{seq}[q], m]}$
    \EndUpon
    \Upon{$\abk{\textit{pl}, \textit{Deliver} \mid s, [k, m]}$}
      \State $\textit{pending} \gets \textit{pending} \cup \{(s, k, m)\}$
    \EndUpon
    \UponCond{$\exists (s, k, m) \in \textit{pending}$ such that $k = \textit{next}[s]$}
      \State $\textit{pending} \gets \textit{pending} \setminus \{(s, k, m)\}$
      \State $\textit{next}[s] \gets \textit{next}[s] + 1$
      \State \Trigger $\abk{\textit{fpl}, \textit{Deliver} \mid s, m}$
    \EndUponCond
  \end{algorithmic}
\end{framedalgo}

Messages that arrive \curlyquotes{too early} wait in \textit{pending} until all the previous messages from the same sender have been delivered. The last handler is not triggered by an event but by a condition: it runs whenever the condition becomes true, possibly several times in a row (e.g.\ when a missing message arrives and unlocks the ones waiting after it).

\paragraph{Formal proof.} We have to prove the four properties.

\begin{proof}[Proof of PL1, PL2, PL3]
  These properties hold directly from the use of the underlying perfect link. For PL1 we only need one more step: if $p$ sends $m$ with sequence number $k$, then $p$ has also sent messages with sequence numbers $1, \ldots, k-1$ to $q$, and by PL1 of \textit{pl} all of them are eventually delivered and added to \textit{pending}. By induction on $j = 1, \ldots, k$, $\textit{next}[p]$ eventually reaches $j$ and the message with sequence number $j$ is delivered, so $m$ is eventually delivered. PL2 holds because $\textit{next}[s]$ only grows, so each sequence number is delivered once (and \textit{pl} never delivers the same pair $[k,m]$ twice). PL3 follows from PL3 of \textit{pl}.
\end{proof}

\begin{proof}[Proof of FIFO]
  By contradiction, suppose that $q$ delivers $m'$ and then $m$, even if $p$ sent $m$ before $m'$. Since $p$ sent $m$ first, its sequence number is smaller: $\textit{seq}(m) < \textit{seq}(m')$. Let $t$ be the instant at which $q$ delivers $m'$: at that moment $\textit{next}[p] = \textit{seq}(m')$. Since $\textit{next}[p]$ starts at $1$ and grows by exactly one unit at each delivery from $p$, it must have been equal to $\textit{seq}(m)$ at some earlier moment, and it could move past that value only by delivering the message with sequence number $\textit{seq}(m)$, i.e. $m$. Thus $m$ has been delivered before $t$, a contradiction.
\end{proof}
